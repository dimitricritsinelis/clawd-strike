# Bazaar area TRANSFORM

One implementing owner per named area. Read `AGENTS.md`, open its reference images, then read `docs/map-design/construction/README.md` and the area's sheet. The construction README is the canonical handoff; the sheet is the design. Layout, assembly dimensions and each area's character schedule are fixed there. Build that scope, including SD-21/22 hand finish and textiles; bounded craft discretion needs no extra approval. Do not redesign, measure from references, make a separate brief, or validate the result in the game during TRANSFORM.

## TRANSFORM <area>

1. Resolve the named area in `docs/map-design/development-plan/README.md`, then read its construction sheet. The progress index maps each link to its own unit and maps the Tea group to its four zones. For a link, build only the matching `LINK_*` site and its owned frontage or return; the other seven links remain untouched. For the Tea group, build and apply the terrace and landing packages from its one sheet; the ramp and stairs are retained with no empty package before setting its single progress row to `built`. Read fixed spec values only when the sheet cites them. The atlas and drawings communicate historical appearance only; they never add construction work or override a sheet.
2. Build the scheduled render-only work and character. Do not turn measured bay axes into identical finish, awning and wear templates. The sheet owns only its named face finish, ground finish and named extras; exempt and adjoining faces remain with their owner.
   - Every future named-area package uses one **section GLB**, built in the plan frame with `facade_kit.Frame(zone rect)`. Package only the faces the sheet owns; never use a section to claim every edge of a zone. A package table with blank `owned faces[]` keeps the runtime walls and adds only its scheduled surface finish.
   - The runtime retains shell apertures, shared backing, structural returns, roof slabs, parapets and roof copings. The section owns the flat face finish, apertured skin and the narrow below-wall-top cornice called `coping` in legacy tasks. Preserve every scheduled opening and do not add a full-footprint roof coping or roof mesh.
   - Use `placements[]` only for scheduled extra geometry such as balconies, cloth, fixtures and skyline pieces. Preserve every `KEEP` placement and its transform. Do not create unlisted props, roofs, connectors or playable surfaces.
   - Use `assets/source/<unit>/build.py` with `assets/source/facade_kit.py`; start from `assets/source/example-section/build.py`. Headless `bpy` is the shipped path. A headless build does not require Blender MCP. If the user requests live MCP work, check its current connection once; do not repeat construction measurements or survey the design. Use only materials, assemblies and assets named by the sheet or construction README.
   - Keep the protected route widths, door floors, clearances, cover, spawns, connectors and elevation unchanged. Do not edit the spec or its design layer to resolve an unscheduled difference; record the area `blocked` with the exact conflict instead.
3. Perform the construction README's bounded assembly inspection: one close-up per distinct assembly, and assembled context including relevant retained roofs, parapets, overheads, signs, dressing and ground. Correct construction defects such as coplanar door faces, unsupported marks or wrong materials. Reuse the current kit, but verify helper output against the SD dimensions; a successful export or object count is not construction proof.
4. Write `assets/source/<unit>/package.json` and apply it with `node scripts/apply-facade-package.mjs apply <unit>`. The package binds only this area's section output, owned faces and scheduled placements.
5. Confirm the exported package and retained interfaces in the README inspection, then set the progress-index row to `built`, or `blocked` with the exact construction conflict. Stop after a single-area request; advance only through the remaining areas of an explicit user-provided queue. `built` means scheduled construction is applied and its assembly/interface evidence exists; it awaits later gameplay, performance and aesthetic validation. Keep `building` for incomplete construction evidence or correctable defects, `blocked` for an exact conflict/dependency. Do not relabel an old build as satisfying a revised sheet. The required headless Blender build and package application are construction steps. Report export, package application, construction inspection and release validation separately; `map:check` does not inspect section triangles, and vertex-only bounds do not prove an empty route volume. Defer `pnpm build`, gameplay checks, gameplay captures, playtests and fresh-eyes review unless the user explicitly requests a bounded check or preview for this task; do not start repeated validation or redesign loops.
