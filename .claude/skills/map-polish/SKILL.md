# Bazaar design and construction

Read `AGENTS.md`, `docs/map-design/construction/README.md`, the named area sheet and its current plan/elevations. Use `handoff.py` from the README to extract numerical inputs for that unit; query needed IDs instead of repeatedly dumping the full-map JSON. Open the relevant reference images. The BZ-04 target defines the full visible area, including unregistered boundary faces, roofs, ground and dressing. Gameplay collision, routes, cover, spawns and playable elevation remain fixed.

## Documentation work

Edit the authored target and common contracts, then regenerate the current sheets/drawings. Do not implement the map or modify live assets/specs merely because an area is mentioned. Validate numerical coverage, ownership, references and output reproducibility. Record requested independent discipline reviews with their actual model/configuration, decisions and reviewed issue. AI document approval is not a licensed seal or an in-game quality claim.

## Architectural design order

Settle each complete building’s use, footprint, storeys, structural bays, principal entrance, shopfront and roof before placing details. Openings follow its measured axes and the sill/head datums of their named room-use groups; galleries, bedrooms, stairs and vents may have different scheduled proportions. Use symmetry where appropriate; explain asymmetry through a stair, addition or trade function. Compose stock, work space, shade and supports together. Variation belongs to buildings and tenancies, not arbitrary offsets. During document authoring, review the neutral elevation and relevant section before defining textures or wear. During implementation, build that approved design without reopening this review.

## TRANSFORM <area or approved queue>

Execution is **implement, review at the end, then quickly correct**. The approved engineering documents should be sufficient for a mostly correct first build. Do not insert mid-build design reviews, repeated audits, scoring cycles or approval gates.

1. Read the requested area's current sheet, drawings and referenced details once. Save one before capture set and baseline runtime authority. Reuse existing trial infrastructure and shared assets; do not resurvey or rebuild unchanged work.
2. Build the complete design and integrate it in one continuous pass using deterministic sources and the named package/producer operations. Complete closures, supports, receivers and returns. Run the builder’s small fixture test before the first full export or after changes to its geometry helpers. Validate supported feature kinds and the frozen issue hash before construction. Run geometry-validity and declared-bounds checks before replacing outputs; failed builds preserve the last valid asset. These are technical tests, not separate review milestones. Only a concrete blocking design contradiction interrupts this pass; record its exact target and measurement.
3. Review once after integration: assemblies/interfaces, exported clear volumes, source/integrated/production hash equality, idempotence, matched actual-game views, collider identity, movement, asset-load errors and relevant regressions. Use the tracked `bz04-trial.mjs --capture-only` runner and saved camera plan. The current R7 task defers performance benchmarking and optimization to a separate task after all 25 areas and shared scope are implemented. Triangle, material, primitive, shadow and draw-call budgets are informational during construction; retain their numerical targets and record readily available counts without blocking exports, integration or completion. Do not add optimization infrastructure, budget approval loops or repeated performance measurements. Report deferred performance work separately from construction checks. Any further user-limited validation is recorded explicitly.
4. Make a short targeted correction pass for observed defects. Rerun affected checks only; do not rebuild unchanged assets, recapture unchanged baselines or commission more reviewers. Keep proven baseline failures separate and never weaken protection to get a pass.
5. Record `built` only with applied construction and assembly/interface evidence; record required in-game checks and final user art acceptance separately. Do not claim user acceptance without it or pause the approved queue for routine area approval. Report elapsed construction and review time separately from one-time infrastructure. On a user stop request, preserve the last tested state and return remaining work promptly; do not start another refinement or lengthy evidence consolidation.

The approved R7 full-map task follows the [canonical queue and readiness contract](../../../docs/map-design/construction/README.md#approved-whole-map-queue-and-readiness), including its authorized worker ownership and shared scope. Continue automatically after each area’s consolidated end review and targeted corrections. A standalone area request stops at that area and its explicitly listed shared interfaces. Do not commit, push or deploy without authorization. A design conflict must be stated with its exact record/measurement and resolved in the target source; no hidden substitute or rebaseline.

When a finish does not read as specified, inspect the picked runtime material, texture/binding and lighting before diagnosing it. A matching material ID or tint is not visual acceptance. Fix implementation defects against the current contract; record proposed art changes in the target and retain their approval status. Report scope/acceptance by verified conditions, not an unsupported percent-complete estimate.
